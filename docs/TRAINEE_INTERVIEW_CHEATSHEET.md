## 2. Блок 1: Manual Testing & Тест-дизайн (Must Have)

### Питання 1: Які основні техніки тест-дизайну ти знаєш і як застосуєш їх у мобільному застосунку?
- **Equivalence Partitioning (Класи еквівалентності):** Розбиття вхідних даних на групи, де програма поводиться однаково. Приклад: поле швидкості дрона від 0 до 100 км/год -> класи: `< 0` (невалідний), `0..100` (валідний), `> 100` (невалідний).
- **Boundary Value Analysis (Граничні значення):** Перевірка на стиках класів: `min-1, min, min+1, max-1, max, max+1`. Для `0..100` це: `-1, 0, 1` та `99, 100, 101`. Баги найчастіше живуть саме на межах (`<` замість `<=`).
- **Decision Table (Таблиця рішень):** Комбінації кількох умов для визначення дії. Наприклад: чи відправляти тактичний сигнал, якщо: (GPS є / немає) AND (Батарея > 10% / <= 10%) AND (Зв'язок є / немає).
- **State Transition Testing (Переходи станів):** Тестування життєвого циклу об'єкта. Наприклад, статус синхронізації офлайн-мапи: `Not Downloaded` -> `Downloading` -> `Paused` -> `Downloaded` -> `Corrupted`.

### Питання 2: Структура ідеального тест-кейсу:
- **ID & Title:** Унікальний ідентифікатор та короткий опис суті.
- **Preconditions:** Початковий стан системи (роль юзера, наявність інтернету, встановлена версія додатку).
- **Steps:** Чіткі пронумеровані дії без двозначності.
- **Test Data:** Конкретні значення (координати, логін, значення сенсора).
- **Expected Result:** Що саме має відбутися після завершення кроків.
- **Postconditions:** Очищення створених даних.

### Питання 3: Структура ідеального мобільного баг-репорту:
- **Title:** `[Android 14][Crash] Опис проблеми + де сталася`
- **Severity / Priority:** Наприклад, `Critical / High`
- **Environment:** Модель девайсу (Samsung Tab Active4 Pro), версія ОС (Android 14 / OneUI 6), версія білда.
- **Steps to Reproduce:** Крок за кроком з 0.
- **Expected vs Actual Result:** Що очікували і що реально сталося.
- **Evidence (Докази):** Скріншот, запис екрана (відео), системні логи (`adb logcat`), знімок DOM-дерева або вивантаження мережевого трафіку.

### Питання 4: Як ти тестуєш вимоги у Figma / PRD на наявність протиріч або «дірок» (Gap Analysis)?
- Перевіряю **граничні стани UI**: що відбувається при дуже довгих текстах (overflow / ellipsis), при відсутності даних (empty states), при помилках бекенду (error states), при завантаженні (skeleton / loading spinner).
- Перевіряю **різні екрани**: як виглядає верстка на 5.5" смартфоні та 10.5" планшеті.
- Порівнюю узгодженість логіки: чи описано поведінку при раптовій втраті зв'язку або відхиленні дозволу на геолокацію.

## 3. Блок 2: Python & pytest (База автоматизатора)

### Питання 1: Що таке фікстури в pytest і для чого потрібен `conftest.py`?
- **Фікстури (`@pytest.fixture`)** готують середовище до тесту (setup) і прибирають за собою після його виконання (teardown за допомогою `yield`).
- **Сфери дії (`scope`):** `function` (за замовчуванням), `class`, `module`, `session`.
- **`conftest.py`** — це кореневий конфігураційний файл pytest, фікстури з якого доступні всім тестам директорії автоматично без явного імпорту.

### Питання 2: Що таке параметризація (`@pytest.mark.parametrize`)?
Це спосіб запустити один і той самий тестовий метод багато разів із різними вхідними даними та очікуваними результатами (ідеально підходить для технік BVA та EP).

### Питання 3: Навіщо потрібен `ruff` і що вимагає PEP 8?
- `ruff` — надшвидкий сучасний лінтер і форматер для Python, написаний на Rust (замінює flake8, black, isort).
- `PEP 8` — офіційний гайд зі стилю коду Python: 4 пробіли на відступ, зрозумілий `snake_case` для функцій і змінних, `CamelCase` для класів, довжина рядка, правильні імпорти.

## 4. Блок 3: API Testing & HTTP

### Питання 1: Базові HTTP методи та статус-коди:
- **Методи:**
  - `GET` — отримання даних (ідемпотентний, безпечний).
  - `POST` — створення нового ресурсу.
  - `PUT` — повне оновлення ресурсу.
  - `PATCH` — часткове оновлення окремих полів.
  - `DELETE` — видалення ресурсу.
- **Статуси:**
  - `2xx (Success):` 200 OK, 201 Created, 204 No Content.
  - `3xx (Redirection):` 301 Moved Permanently, 304 Not Modified.
  - `4xx (Client Errors):` 400 Bad Request, 401 Unauthorized (немає токена), 403 Forbidden (немає прав), 404 Not Found, 422 Unprocessable Entity.
  - `5xx (Server Errors):` 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable.

### Питання 2: Як читати специфікацію OpenAPI / Swagger?
- Звертаю увагу на **Base URL**, доступні **Endpoints** та відповідні **HTTP методи**.
- Перевіряю обов'язкові **Headers** (наприклад, `Authorization: Bearer <token>`, `Content-Type: application/json`).
- Дивлюся на **Request Body Schema** (типи даних, обов'язкові поля `required`, обмеження `min/max`) та схему можливих відповідей (`200`, `400`, `401`).

## 5. Блок 4: Appium & Мобільна специфіка (Android / iOS)

### Питання 1: Чим Appium відрізняється від Selenium?
- **Selenium** працює з браузерами на десктопі через драйвери браузерів (ChromeDriver, GeckoDriver).
- **Appium** розширює протокол WebDriver (W3C Mobile JSON Wire Protocol) для нативних, гібридних та мобільних веб-додатків. Під капотом він транслює команди у нативні фреймворки платформи:
  - На **Android** — через `UiAutomator2`.
  - На **iOS** — через `XCUITest` (Apple).

### Питання 2: Який пріоритет локаторів в Appium і чому?
1. **`AppiumBy.ACCESSIBILITY_ID`** — найвищий пріоритет. На Android це атрибут `content-desc`, на iOS — `accessibilityIdentifier`. Він кросплатформний, не залежить від локалізації та верстки.
2. **`AppiumBy.ID`** — швидкий і надійний ідентифікатор ресурсу (`resource-id`).
3. **`AppiumBy.ANDROID_UIAUTOMATOR` / `IOS_PREDICATE`** — нативні селектори рушіїв.
4. **`AppiumBy.XPATH`** — найнижчий пріоритет. Використовувати тільки відносний XPath (`//android.widget.TextView[@text='Save']`). Суворо уникати абсолютних шляхів (`/hierarchy/...`), бо вони надзвичайно крихкі.

### Питання 3: Чому не можна використовувати `time.sleep()`?
- `time.sleep()` блокує потік на фіксований час. Якщо додаток завантажився швидше — тест безпідставно марнує час. Якщо повільніше (через лаг емулятора) — тест впаде.
- Слід використовувати **`WebDriverWait`** з **`expected_conditions`** (наприклад, `visibility_of_element_located` або `element_to_be_clickable`).

### Питання 4: Як виконувати свайпи та скроли в сучасному Appium?
Через стандартизований **W3C Actions API (`ActionChains`)**. Координати точок дотику обчислюються **динамічно у відсотках** від `driver.get_window_size()` (наприклад, старт: 50% ширини і 80% висоти, кінець: 50% ширини і 20% висоти для свайпу вгору). Жодного хардкоду пікселів!

## 7. Блок 6: Git & Командна робота

### Питання: Який стандартний флоу роботи з гілками та вирішення конфліктів?
1. Створення фіче-гілки від `main`/`develop`: `git checkout -b feature/login-bva-tests`.
2. Внесення змін, перевірка лінтером: `ruff check .`.
3. Атомарний коміт зі змістовним повідомленням: `git commit -m "feat(login): add BVA boundary tests for credentials"`.
4. Відправка на сервер: `git push origin feature/login-bva-tests` та створення Merge Request (MR).
5. **Вирішення конфлікту:** роблю `git fetch origin`, переключаюся або роблю `git merge origin/develop` (чи `git rebase origin/develop`), вручну в IDE розбираю конфліктні маркери `<<<<<<<`, `=======`, `>>>>>>>`, проганяю тести, щоб переконатися, що нічого не зламано, і роблю `git commit` та `git push`.

## 8. Блок 7: Специфіка Military / Defense-домену (НАТО/США)

Оскільки проєкт для військових замовників США/НАТО, на інтерв'ю оцінять твоє розуміння польової специфіки:
- **Zero Internet Dependency (Offline First):** У бойових або польових умовах додаток має повністю функціонувати без інтернету, зберігати дані у локальній БД і синхронізувати чергу змін лише при появі зв'язку.
- **Interrupts & Battery:** Будь-які переривання (дзвінки рації, зміна орієнтації планшета в руках, енергозбереження) не повинні скидати координати або введені дані.
- **Безпека:** Відсутність чутливих координат чи ключів у відкритих системних логах (`logcat`), які можуть бути прочитані шкідливим ПЗ.
